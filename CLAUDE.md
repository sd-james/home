## Project rules

- **This app must run in Expo Go.** Do not add custom native code, `ios/`/`android/` folders, config plugins that change native code, or any library that isn't bundled in Expo Go. Use `npx expo install <package>` and confirm the package works in Expo Go before adding it. If a feature needs a development build, say so instead of adding it.
- **Changes go to `main`.** Commit and push directly to `main` — no feature branches or pull requests; every push to `main` runs `.github/workflows/eas-update.yml`, which publishes an EAS Update to the `main` channel so it opens in Expo Go at `exp://u.expo.dev/08996c47-64d7-45fd-b395-a40390e55765?channel-name=main`.
- The app is on SDK 58 (pre-release) because Android Expo Go 57.0.9 can't open private EAS updates (it drops the sign-in); Expo Go 58.0.2+ is installed from https://github.com/expo/expo-go-releases. Move to the stable 58 release once it's out.
- Keep the Expo SDK at a version Expo Go supports. `runtimeVersion` uses the `sdkVersion` policy (`exposdk:<sdk>`), which is what lets Expo Go load the published updates — don't change it.
- Before pushing, run `npx tsc --noEmit`, `npx expo lint` and `npx expo-doctor`.
- `.npmrc` sets `legacy-peer-deps=true` because React Native 0.88 is a release candidate and fails strict peer ranges (e.g. AsyncStorage's `>=0.65 <1.0`). Remove it once SDK 58 is stable.

## App structure

Three bottom tabs: **Devices**, **Visitor Code**, **Settings**. All data is stored on the phone with AsyncStorage.

```
src/
  app/                        Expo Router routes (screens only)
    _layout.tsx               Root stack + AppStateProvider
    (tabs)/_layout.tsx        Bottom tabs
    (tabs)/index.tsx          Devices: list, add/edit/delete, export/import
    (tabs)/visitor.tsx        Visitor Code: request, read reply, share, recent codes
    (tabs)/settings.tsx       Settings
    device/[id].tsx           One device's weekly schedule
  components/
    ui.tsx, theme.ts          Shared building blocks (Button, Chip, Card, Field, Sheet)
    pickers.tsx               TimePicker, OnOffPicker, DayPicker, UsesStepper
    devices/                  Sheets for the Devices feature (device form, event editor,
                              copy day, import)
  lib/                        Plain TypeScript, no React — keep logic here and testable
    types.ts                  Device, ScheduleEvent, Settings, VisitorCode
    days.ts                   Day constants (MON..SUN), time helpers
    schedule.ts               Add/edit/delete/copy schedule events
    googleHomeScript.ts       ALL Google Home script reading and writing
    visitorCode.ts            Estate SMS request/reply format, message template
    sms.ts                    Compose SMS, pick a contact (expo-sms, expo-contacts)
    settings.ts               Default settings
  state/
    createPersistedStore.tsx  React context whose value is saved to AsyncStorage
    stores.tsx                Devices, settings and recent-code stores (+ reviving old data)
```

- Screens stay thin: put logic in `src/lib/` and shared state in `src/state/stores.tsx`. A new feature (e.g. shared lists) gets its own route(s), a `lib/` module, a store in `stores.tsx` and, if needed, a `components/<feature>/` folder.
- Stored data is revived through the `revive*` functions in `stores.tsx`, so old data keeps loading when fields change. Change a storage key's version only for a breaking change.
- Sheets (`components/devices/*Sheet.tsx`) mount their contents only while open so their form state starts fresh each time; follow that pattern instead of resetting state in effects (the linter's React Compiler rules flag that).
- Keep it usable with one thumb: big buttons (`TOUCH` = 52px minimum), bottom sheets, few taps.

## Google Home schedules

Expo Go can't talk to Google Home, so schedules are exchanged as **Google Home automation scripts** (the YAML in the script editor at https://home.google.com). All reading and writing of scripts is in `src/lib/googleHomeScript.ts`, so a direct Google Home connection can later replace it behind the same functions.

- A device is identified in scripts as `"<name> - <room>"` (just `<name>` without a room) and must match the names in Google Home exactly.
- Each device's events are kept unique per (time, action) with a list of days (`normalizeEvents` in `lib/schedule.ts`), so export makes exactly one automation per device, time and action:

```yaml
metadata:
  name: Home app schedules
  description: Generated by home app
automations:
  - starters:
      - type: time.schedule
        at: "08:00"
        weekdays: [MON, TUE, WED, THU, FRI]
    actions:
      - type: device.command.OnOff
        devices: Kettle - Kitchen
        on: true
```

- Export is written by hand (not `js-yaml`'s dump) to keep exactly this layout; `at` is always quoted.
- Import parses with `js-yaml` (v5, YAML 1.2, so `08:00` stays a string), takes `time.schedule` starters with `device.command.OnOff` actions, creates missing devices, and reports anything else (other starters, sunrise/sunset, conditions, other actions, unknown weekdays) as issues instead of dropping it silently. The user is asked before existing events are replaced.

## Estate visitor codes (Les Maisons)

- Request: text the request format (default `TAP{uses}`, e.g. `TAP9`) to the estate number (default `0637127256`). The app opens the SMS app with this filled in; the user taps send.
- Reply, e.g.: `Les Maisons TAP code 61359 valid for 9 uses till 2026-10-04 23:59:59`
- `parseReply` in `lib/visitorCode.ts` is forgiving: the code is the number after "code" (else the first 4–8 digit number that isn't part of a date), uses is the number before "uses/entries/times", and the expiry is a `YYYY-MM-DD[ HH:MM[:SS]]` date (local time; date only means 23:59:59).
- The visitor message comes from the template in Settings with `{code}`, `{uses}` and `{expiry}` filled in. The user can edit it for a single share.
