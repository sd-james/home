# Home app

@AGENTS.md

> **This app no longer runs in Expo Go.** It is its own Android app ("Home", package `com.stevenjames.home`) built with EAS Build, because it uses a local native module (`modules/sms`) and SMS permissions. Android only for now.
>
> - **TypeScript/JS changes** (anything in `src/`, and JS-only packages) reach the installed app as an **update**: push to `main`.
> - **Changes to native code** (`modules/*/android`), **permissions**, **packages with native code**, or **native settings in `app.json`** (package name, permissions, plugins, icons, `updates`, `runtimeVersion` …) need a **new build**: run the **"Build Android"** action (Actions tab → Build Android → Run workflow), then install the new APK. Say so whenever a change needs a build.

## Project rules

- **Changes go to `main`.** Commit and push directly to `main` — no feature branches or pull requests. Every push runs `.github/workflows/eas-update.yml`: typecheck, lint, tests, then `eas update --channel main --platform android`.
- **Builds:** `.github/workflows/build-android.yml` ("Build Android", started by hand) runs `eas build --platform android --profile preview --non-interactive --no-wait`. The `preview` profile in `eas.json` makes an internally distributed APK on channel `main`. The Android signing key is kept on Expo's servers (created on the first build).
- **Runtime version uses the `fingerprint` policy**: a hash of everything native (native code, native packages, native app config). An update only reaches builds with the same fingerprint. So if a commit changes the fingerprint, its update reaches no installed app until a new build is installed. Check before pushing with `npx expo-updates fingerprint:generate --platform android` (compare with the previous commit) when unsure.
- **Updates in the app** (`src/lib/updates.ts`): the app checks for an update when it opens and applies it straight away (reloads). The native automatic check is set to `ON_ERROR_RECOVERY` so it doesn't download twice. Settings → "Check for updates" does the same on demand and shows the current update's date.
- Use `npx expo install <package>` to add packages (SDK-compatible versions). A package with native code needs a new build. Watch out: `expo install` may also add a config plugin to `app.json`, which changes the fingerprint (= needs a build); remove it if it isn't needed, and compare the fingerprint before and after.
- Never create or edit `android/`/`ios/` by hand (they're generated by `npx expo prebuild`, and gitignored). Native behaviour goes in `app.json`, config plugins or the local module in `modules/`.
- Before pushing, run `npx tsc --noEmit`, `npx expo lint`, `npm test` and `npx expo-doctor` (and `npm test` in `firebase/functions` when it changes).
- The app is on Expo SDK 58, still a pre-release (React Native 0.88 release candidate). Move to the stable 58 release once it's out. Until then `.npmrc` sets `legacy-peer-deps=true`, because the RC version fails strict peer ranges (e.g. AsyncStorage's `>=0.65 <1.0`).

## App structure

Four bottom tabs: **Devices**, **Tasks**, **Visitor Code**, **Settings**. Devices, settings and visitor codes are stored on the phone with AsyncStorage; household tasks are shared through Firebase (see below). The screen rotates (`orientation: default`); scrolling screens and sheets pad by the left/right safe-area insets because the 3-button navigation bar moves to the side in landscape.

- Screens stay thin: put logic in `src/lib/` and shared state in `src/state/stores.tsx`. A new feature (e.g. shared lists) gets its own route(s), a `lib/` module, a store in `stores.tsx` and, if needed, a `components/<feature>/` folder.
- Stored data is revived through the `revive*` functions in `stores.tsx`, so old data keeps loading when fields change. Change a storage key's version only for a breaking change.
- Sheets (`components/devices/*Sheet.tsx`) mount their contents only while open so their form state starts fresh each time; follow that pattern instead of resetting state in effects (the linter's React Compiler rules flag that).
- **Navigation bar (Pixel, Android 15+):** the app is drawn edge-to-edge and Android reports the navigation bar's height correctly as the bottom safe-area inset (48dp for 3-button navigation). What looked like the tab bar overlapping the buttons was Android's grey *contrast scrim* over that strip; it is turned off with the `expo-navigation-bar` plugin (`enforceContrast: false`, dark buttons) in `app.json`, so the white tab bar runs under the buttons. The tab bar's height and bottom padding are set from the inset in `(tabs)/_layout.tsx`, with a small gap below the labels. Use `useAppInsets()` (`components/insets.ts`) for bottom spacing.
- Icons: `@expo/vector-icons` (MaterialCommunityIcons). It is JS + fonts on top of `expo-font`, which is already in the build, so it doesn't change the fingerprint.
- Keep it usable with one thumb: big buttons (`TOUCH` = 52px minimum), bottom sheets, few taps.

## Household tasks (Firebase)

Everyone in the household sees the same tasks and reminders and gets push notifications. Everyone is on Android.

- **Firebase project** (the user's): Firestore (database), Authentication (Anonymous provider), Cloud Functions on the Blaze plan, Cloud Messaging. The app uses the **Firebase JS SDK** (no native code): config in `src/lib/firebaseConfig.ts` (web app config; not secret). `google-services.json` (root) is only for push (FCM) via `expo-notifications`; changing it needs a build. The FCM V1 service account key is uploaded to EAS (expo.dev → Credentials) so Expo's push service can deliver.
- **People:** each phone signs in anonymously (persisted in AsyncStorage). One person creates a household (gets a join code like `K7M-4QX`), others join with it. Households and membership are only changed by Cloud Functions (`createHousehold`, `joinHousehold`, `leaveHousehold`, `updateHousehold`); the rules forbid client writes there.
- **Data:** `households/{id}` (name, joinCode, memberIds, members), `households/{id}/tasks/{id}` (written by the app, validated by the rules), `households/{id}/devices/{deviceId}` (Expo push tokens), `users/{uid}` → householdId, `joinCodes/{code}` → householdId.
- **Tasks:** title, notes, due day (`YYYY-MM-DD` or none), reminder (`remindAt` + `reminderPending`), assignee, repeat (none/daily/weekly/monthly). Ticking a repeating task moves it to its next date instead of closing it. Logic is in `src/lib/tasks.ts` (tested).
- **Notifications** (functions, via Expo's push API, Android channel `household`): a new task notifies everyone except its creator; `sendDueReminders` runs every minute and sends due reminders to the assignee, or everyone. Tapping a notification opens Tasks.
- **Functions region** `europe-west1` (`FUNCTIONS_REGION` must match). Deploys run from `.github/workflows/deploy-firebase.yml` on pushes that change `firebase/`, with the `FIREBASE_SERVICE_ACCOUNT` secret; without it the job skips. Changes in `firebase/` don't affect the app's fingerprint.
- Test the rules with the Firestore emulator and `@firebase/rules-unit-testing` when changing them (deny outsiders, members only write tasks/own devices).

## Google Home APIs (direct connection)

Replacing the script copy/paste (in progress). Step 1, done: connect, list on/off devices with rooms, switch them (`components/devices/GoogleHomeCard.tsx`). Step 2, next: schedules saved as automations through the Automation API, replacing `googleHomeScript.ts`.

- **SDK:** Google Home APIs for Android, `play-services-home` + `play-services-home-types` 17.1.0. Not on Google Maven: downloaded from https://storage.googleapis.com/home_sdk_android/home.android.sdk_1_11_0.zip and kept in `modules/googlehome/android/maven` (javadoc and checksums removed); the module's `build.gradle` adds that repo to every Gradle project. Compiled with a newer Kotlin than React Native's, so the module uses `-Xskip-metadata-version-check`.
- **Access:** an Android OAuth client in the user's Google Cloud project (package `com.stevenjames.home` + the EAS keystore's SHA-1), consent screen in testing mode with the user as test user. No Play Store or Google review needed for test users.
- **Consent:** `registerActivityResultCallerForPermissions` must run in the activity's `onCreate`, done by `GoogleHomePackage`'s `ReactActivityLifecycleListener`. The app gets one home (structure); "Change home or devices" re-opens Google's consent screen.
- **Only registered device types/traits are visible** (`GoogleHome.kt` FactoryRegistry): plugs, lights and light switches with `OnOff`. Add types there (new build) if a device is missing.
- **Automation API limits** (for step 2): an app can only read automations it created itself; 64 automations per home; scheduled starters need the home to have a street address in the Google Home app.

## Google Home schedules (scripts — being replaced)

The app can't talk to Google Home directly (yet), so schedules are exchanged as **Google Home automation scripts** (the YAML in the script editor at https://home.google.com). All reading and writing of scripts is in `src/lib/googleHomeScript.ts`, so a direct Google Home connection can later replace it behind the same functions.

- A device is identified in scripts as `"<name> - <room>"` (just `<name>` without a room) and must match the names in Google Home exactly.
- Each device's events are kept unique per (time, action) with a list of days (`normalizeEvents` in `lib/schedule.ts`), so export makes exactly one automation per device, time and action:

```yaml
metadata:
  name: Home app schedules
  description: Generated by home app
automations:
  - starters:
      - type: time.schedule
        at: "08:00"
        weekdays: [MON, TUE, WED, THU, FRI]
    actions:
      - type: device.command.OnOff
        devices: Kettle - Kitchen
        on: true
```

- Export is written by hand (not `js-yaml`'s dump) to keep exactly this layout; `at` is always quoted.
- Import parses with `js-yaml` (v5, YAML 1.2, so `08:00` stays a string), takes `time.schedule` starters with `device.command.OnOff` actions, creates missing devices, and reports anything else (other starters, sunrise/sunset, conditions, other actions, unknown weekdays) as issues instead of dropping it silently. The user is asked before existing events are replaced.

## Estate visitor codes (Les Maisons)

- Request: text the request format (default `TAP{uses}`, e.g. `TAP9`) to the estate number (default `0637127256`).
- Reply, e.g.: `Les Maisons TAP code 61359 valid for 9 uses till 2026-10-04 23:59:59`
- **Automatic flow** (Android build with the `HomeSms` module): "Get code" asks for SMS permissions the first time (with an explanation), sends the request with `SmsManager`, then waits up to 2 minutes for a reply from the estate number. It listens for incoming SMS (`SMS_RECEIVED` broadcast → `onSmsReceived` event) and also reads the inbox every 4 seconds in case the listener misses it. On a reply it shows the code, copies it to the clipboard, saves it to recent codes and scrolls to the share options (Share sheet, Copy code).
- No manual flow: if permission is refused, sending fails or no reply arrives in time, the screen says why and offers "Keep waiting" (after a timeout) or "Open phone settings" (permission blocked).
- Recent codes disappear once expired (`isStillValid` in `lib/visitorCode.ts`; codes without a readable expiry are kept for 24 hours). They are filtered when shown, saved and loaded.
- `parseReply` in `lib/codeReply.ts` is forgiving: the code is the number after "code" (else the first 4–8 digit number that isn't part of a date), uses is the number before "uses/entries/times", and the expiry is a `YYYY-MM-DD[ HH:MM[:SS]]` date (local time; a date alone means 23:59:59). `isSameNumber` matches the sender loosely (`063…`, `+2763…`, spaces) by comparing the last 9 digits. Add a test to `codeReply.test.ts` for any new reply format.
- The visitor message comes from the template in Settings with `{code}`, `{uses}` and `{expiry}` filled in. The user can edit it for a single share.
